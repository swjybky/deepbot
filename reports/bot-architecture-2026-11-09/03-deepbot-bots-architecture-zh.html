DeepBot 整体设计：会管活、也会干活的 IM Bots

把 OpenBot 的「持久 Bot」和 DSH 的「授权任务」合成一个结构：你只跟 Bot 说话，Bot 对每件事负责到底；活可以它自己干，也可以派给 Hermes Agent、T3 Code 或真人。全文分两部分：最小 MVP（个人 Bot）和未来扩展（群聊）。

设计日期：2026-11-10
依据：报告 01（OpenBot）、报告 02（DSH Superagent）；本地代码 packages/agent、apps/desktop；Pi Durable 1.5.0 README；T3 Code、Hermes Agent、ACP、Claude Agent SDK 的公开文档（2026-11-10 读取）

核心判断：Bot 是负责人，执行者是干活的路径。会话、事项、执行分三层：会话层是 IM，随时说、随时回；事项层是 Bot 的账本，记着接了什么、派给谁、卡在哪；执行层是可替换的执行者，可以是 Bot 自己、外部智能体或真人。Bot 的前台永远腾得出手回话，成块的活全部在后台跑。

标记：已核验在本地代码或对方官方文档里确认过；设计本文提出的方案；待定需要你拍板。外部产品没有实际安装、连接做端到端验证；Pi Durable 的用法依据它的 README，还没有写代码验证。本次没有改动任何应用代码。

1. 我对需求的理解

你的原话是语音转写的，有几处我按上下文还原了：「ARM 通信」读作 IM 通信；「不像 DeepSeek」读作不像 DSH Superagent；「human agent」有两种读法，Hermes Agent 这类外部智能体，或者真人。两种读法在这份设计里都是执行者，结构上不冲突，所以都覆盖了。

你说的设计上的含义
基于 IM 通信，不是一问一答消息和回复解耦：你随时发，Bot 可以回 0 到多条，也可以在没人问的时候主动汇报。见 第 4 节。
不像 DSH 只管理会话，还能管理别的智能体DSH 的主会话只做路由，干活的只有它自家的 Session。DeepBot 把「干活的路径」抽象成执行者端口，Hermes Agent、T3 Code、真人都是它的实现。见 第 7 节。
Bot 是管活的，也可以实际去干活「自己干」是默认执行者，和外部执行者走同一套派工流程，区别只是活跑在 Bot 自己的后台会话里。见 第 2 节、第 6 节。
有些动作，用户会要求走别的路径路由有优先级：你这次点名 > 你立过的规矩 > Bot 判断 > 自己干。干到一半也能改派，事项不变。见 7.4。
先个人，后群聊单聊按「两个成员的群」建模，消息存作者、不存角色。到群聊时，别的 Bot 只是又一种执行者。见 第 9 节、第 10 节。

2. 三个核心决定

决定一：会话、事项、执行分三层

设计会话层只管谁说了什么。事项层是 Bot 的账本，记录接了哪些活、各自派给谁、卡在哪。执行层是可替换的执行者。三层各有自己的状态，互不冒充：模型回了一句话不等于事办完了，执行者说完成了也不等于 Bot 已经验收。

决定二：Bot 的前台永远腾得出手

设计每个 Bot 在每个会话里有一条前台线，只做管理和顺手的小事，有轮数预算。成块的活一律放到后台线去跑，包括 Bot 自己干的。后台跑着三件事的时候，你发一句话，Bot 仍然马上能接。

决定三：所有干活路径实现同一个执行者端口

设计派工、收汇报、验收、改派这套管理逻辑只写一遍，不随执行者分叉。新接一种智能体，就是写一个适配器，再声明它有哪些能力。

方案结果

4. IM 语义：为什么不是一问一答

一问一答DeepBot
发消息Bot 回完才能发下一条随时发。消息先入账、立即显示，再决定要不要唤醒 Bot
连发几条每条各触发一次回答合并成一次唤醒。Bot 已经在动手时，新消息在下一个工具回合插进去
回复数量恰好一条0 到多条：可以只点个表情，可以先回执、后交付
谁能开口只有用户消息能触发执行者汇报、定时、外部事件都能让 Bot 主动说话
同时几件事一件，按顺序多件并行。引用哪条，就是在对哪件事说话
进度刷在回答里留在事项卡片上原地更新。消息只用于四种情况：回执、要你决定、交付、干不下去
状态一个 busy 真假每件事各自的阶段：排队、执行中、等你、验收中、已交付

4.2 输出契约：Bot 怎么「说话」

设计一问一答的系统里，模型的最终文本就是回复。这里把「说话」变成 Bot 的一个明确动作：

  • 最终回答文本：发成一条消息；为空就不发。
  • say：中途就发一条，用于回执和分段交付。
  • ask：发一张提问卡片，要你做决定、批准或动手；对应的事项进入「等你」。
  • pass：这一轮不说话，比如只是收到了一条它自己能处理的汇报。
  • 表情回执：表示看到了，不占一条消息。
  • 工具调用之间的自言自语不外发，只进工作日志。

连发合并的实现先做两样：短窗口防抖（起步值一两秒，可调），以及忙时插话。「Bot 还没动手就重想」留作后续优化。

5. 核心对象

设计「事项」对应报告 02 的 Ticket / Task。现有界面右栏「即将进行」里的定时项，这里叫「例行」，它只是一种触发器，每次触发开一个事项。

对象是什么关键字段与不变量
Bot常驻联系人，也是负责人botId、人设指令、模型、工作目录、权限开关、可用执行者、路由规则。身份不绑定进程，也不绑定某个模型会话。
会话 Thread单聊或群threadId、kind（dm / group）、members（人或 Bot）。单聊就是两个成员的会话。
消息 Message会话里的一条messageId、author（person / bot / system）、kind（text / ask / result / notice）、replyTo、workId、requestId。存作者，不存 user / assistant 角色。
事项 Work一件被接下的活workId、ownerBotId、threadId、目标、验收标准、范围、state、revision。负责人唯一，不随改派变。
派工 Assignment事项的一次执行绑定assignmentId（幂等键）、executorId、sessionRef、派工单、state、attempt。一件事可以有多次派工。
执行者 Executor干活的路径executorId、kind（self / harness / human / bot）、能力声明、所在电脑、是否可用。
汇报 Report执行者 → Botkind（progress / question / permission / artifact / ready / blocked / failed）、证据引用。结构化，不靠猜文字。
提问 AttentionBot → 人，要一个决定attentionId、workId、问题、选项、kind（决定 / 批准 / 要你动手）、答复。一次性，答过即失效。
路由规则 RouteRule什么动作走哪条路match（动作类别、目录、关键词）、executorId、是否先问、来源消息、enabled。
例行 Routine定时触发器计划、提示、enabled。每次触发开一个事项。
记忆与产物长期事实；文件、链接、改动记忆带证据引用和 revision。产物带 hash，消息只引用它；它就是右栏的「资料库」。

6.1 管理者的四件事

做什么
派把活写成派工单：目标、背景（引用消息和文件，不贴整段聊天）、范围与禁区、验收标准。选好执行者，在一次提交里同时记账和创建派工。
盯进度只更新卡片，不唤醒 Bot，也不发消息。只有提问、请求批准、完成、受阻、失败才唤醒 Bot。
挡执行者的问题先到 Bot。凭会话和记忆能答的，Bot 直接答；涉及授权、花钱、对外发布，或者它确实不知道的，才变成给你的提问卡片。
验执行者说「完成」只是一条汇报。Bot 按验收标准核对证据：文件在不在、命令输出是什么、链接能不能开。通过才交付；不通过就退回，退回次数有上限，超了如实告诉你。

6.2 一条消息归到哪件事

  1. 引用或回复了某张事项卡片，或某条挂着事项的消息：归那件事。这一步是确定性的，不问模型。
  2. 正好有一个提问在等你，而这条消息在回答它：归那件事。
  3. 其余交给 Bot 前台判断：直接回答、顺手做掉、开新事项，或者并入已有的事。

能确定的不让模型猜，只有新话题才需要判断。

6.3 三层状态

状态层取值表达什么
事项open → ended（done / failed / cancelled）；回复结果可以重新打开这件事还在不在
派工pending → running → ended（completed / failed / cancelled / interrupted）这一次执行绑定的寿命
给人看的阶段（派生）排队、执行中、等你、验收中、已交付、失败、已取消此刻在等谁、为什么没往前走

6.4 前台预算与并发

设计前台一轮的工具回合数有上限（起步值，可调）。到了上限还没做完，说明它不是小事，必须开事项转到后台。后台同时跑的派工也有上限，人的消息永远优先于新派工。

7.3 能力不齐时怎么降级

执行者缺的能力Bot 怎么处理
不能运行中插话补充先记在事项上，等这一轮结束再发。你说「马上改」，就取消重派。
不能取消事项标成「已放弃，等对方收尾」，并告诉你去对方界面停。
重启后接不回这次派工记为中断。开一次新派工，附交接包（已完成的步骤、产物、未决问题），并要求先核对现场再继续。
不能转发审批审批发生在对方界面，卡片显示「等你 · 去 T3 Code 确认」。这类执行者只接你点名的活，或规则明确放行的活。
没有实时进度卡片只显示阶段和最后一次汇报。

7.4 谁来干：路由

设计优先级从高到低：

  1. 你这次点名。「用 T3 Code 做」「你自己来」「这个我自己弄」。
  2. 你立过的规矩。例如：改代码仓库 → T3 Code；长时间调研 → Hermes Agent；对外发布 → 先问我。
  3. Bot 判断。按各执行者的能力说明和以往的结果选。
  4. 兜底：自己干。
  • 规矩怎么来。在设置里手写，或者在聊天里说一次「以后这类都交给 Hermes」。Bot 把它复述成一条规则，你确认之后才生效。规则带着来源消息，随时可以关。
  • 规矩可以细到动作。一件事里的某个动作可以单独走另一条路。比如「写推文并发布」：写由 Bot 自己来，发布按规矩交回给你。做法是在事项下开一个子事项，只挂那一个动作。MVP 只允许一层子事项。
  • 改派。干到一半说「别自己干了，换 T3 Code」：当前派工取消，Bot 整理交接包，开一次新派工。事项编号、会话里的卡片、已有产物都不变。换的是执行者，不是这件事。

7.5 权限：同一套开关，对所有执行者生效

已核验设置里已经有「Bot 可以做什么」四个开关（ui/state/preferences.ts）。设计它们按动作类别落在代码闸上，不写在提示词里，也不因为换了执行者就失效。

现有开关闸的行为
读取和保存本地文件关闭时拒绝文件类动作；开启时限定在你连接的文件夹。
使用浏览器关闭时拒绝浏览器类动作。
发布或发送前先问我对外发布、发送类动作必须先拿到一次批准（提问卡片）。批准绑定到具体事项和具体内容，只能用一次。
允许删除文件默认拒绝删除。

闸有多硬，取决于执行者：

  • 自己干：硬。每次工具调用之前由钩子检查。
  • ACP 和 SDK 类：较硬。对方发起的权限请求转给 Bot 裁决，由它按开关放行、拒绝或问你。前提是以「需要批准」的模式启动对方，否则同样是弱约束。
  • T3 Code：弱。上限是你在 T3 Code 里批准给 DeepBot 的权限级别。DeepBot 只能在派工前检查，并把约束写进派工单。界面上要标出来。

批准记在账本里：被拦下的动作先报「需要批准」，Bot 发提问卡片；你同意之后批准写入事项，执行者重试时，闸读到批准才放行。所以重启不丢批准，一次批准也用不了两次。

第二部分9. 未来扩展：群聊

9.1 什么不变，什么新增

不变新增
消息格式（本来就带作者）会话成员多于两个；群有自己的公共记录，每个 Bot 在每个群里有自己的前台线
事项、派工、汇报、提问唤醒规则：哪条消息唤醒哪个 Bot
执行者端口两种新执行者：别的 Bot、群里的其他人
权限闸、路由规则授权：谁提的、能读什么、能做什么、回到哪儿
协议事件、前台与后台分线群记忆、外部 IM 入口与出站队列、后台常在线

9.2 谁被唤醒

设计群里不是每条消息都唤醒每个 Bot。入账之后先过一道确定性的 Gate：

  1. @ 了某个 Bot：唤醒它。
  2. 回复某个 Bot 的消息，或引用它负责的事项卡片：唤醒它，消息归那件事。
  3. 回答某个 Bot 的提问卡片：唤醒它。
  4. 以上都不是：交给这个群的主持 Bot 做一次轻量分诊。它只有管理工具，可以回一句、派给别的 Bot，或者不理。没设主持 Bot，就谁也不唤醒。
  5. Bot 发的消息不唤醒别的 Bot。Bot 之间只通过派工交接，不靠在群里喊话。

9.3 一事一主，Bot 之间也是派工

  • 每件事有且只有一个负责 Bot，群里的人随时看得到是谁。
  • Bot A 把活派给 Bot B：对 A 来说，B 就是执行者 bot:B，走同一个端口。B 在自己的线上把它当作一件事来办，结果作为汇报回到 A，由 A 向提出的人交付。
  • 两种交接：派子活，负责人不变；移交，负责人换成对方，群里出一条系统提示。
  • 防循环：事项记着派工链，深度有上限，不能派回链上已经出现过的 Bot。
  • 真人执行者扩大到群成员：Bot 可以把一个动作 @ 给某个人，派工等这个人答复。超时只提醒一次，然后向提出的人说明卡在谁那儿。

9.4 授权：上下文可以广，动作必须窄

单聊里只有你一个人，所有请求天然是你授权的。群聊里必须回答三个问题，分开存、分开查：

范围回答的问题规则
contextScope能读什么这个群的记录、这件事的资料。单聊历史和 Bot 主人的私有资料默认不可读。
actionScope能做什么群成员可以提只读、调研、群范围内的事。碰到对外发布、删除、花钱、动主人的私有资料，变成给主人的提问卡片。
replyScope回到哪儿回到提出请求的那个话题，不串到别的会话。
  • 每件事记下提出人和授权依据：谁提的、当时的规则版本、允许的动作类别。后续消息可以补充信息，不能自动扩大授权。
  • 群里任何人贴的文字都是资料。有人贴「忽略之前的规则」，它进上下文，但改不了 actionScope。
  • 主动性分三档，沿用 DSH：off；observe，只记录「本来会接」，不动手；auto，命中启用的规则才接。默认 observe。

9.5 上下文与记忆

  • 给 Bot 的是上下文包：群摘要、最近原文、被引用的消息、上次之后的增量，不是整段历史。摘要带原消息 ID，可以回读。
  • 各 Bot 不共用模型上下文。共享的是公共记录、事项结果和产物。
  • 记忆分两种归属：群记忆和 Bot 私有记忆。隔离是单向的：群里学到的不自动进私有记忆；私有记忆能不能带进群，由 Bot 主人决定，默认不带。

9.6 外部 IM 与常在线

  • 外部 IM 是又一种入口。适配器把飞书群、Slack 频道映射成会话，外部消息 ID 就是幂等键；回复走出站队列，带平台的幂等键，回到原话题。
  • 三种成功分开记：已接收、已办完、已送达。办完了但没送达，要看得见、能重试。
  • 外部身份和桌面身份不自动合并权限。
  • 已核验Pi Durable 的存储同一时间只能由一个进程持有。所以要接外部 IM，就得让一个独立的后台服务成为唯一的执行宿主，桌面端变成它的客户端。
  • 多台电脑：执行者带「所在电脑」字段。远端机器上的执行者经它自己的服务接入，例如通过 T3 Code 的 MCP 端点连到另一台机器上的环境。

9.7 演进阶段

阶段新增什么验收
G1
内部群：我和多个 Bot		群的公共记录与各 Bot 前台线分离；唤醒规则；bot: 执行者；防循环。仍然只有你一个人，不需要授权模型群里说一句不 @ 任何人，只有主持 Bot 被唤醒。@A 的活 A 派给 B，结果回到 A，由 A 交付。A 和 B 不会互相刷屏。
G2
多人与外部 IM		先接飞书；身份、授权、三种范围、出站队列、后台常在线非主人要求对外发布，变成给主人的审批。同一条外部消息重投只开一件事。关掉桌面后群里 @Bot 仍有回应，结果回到原话题。
G3
主动性与群记忆		observe 和 auto 模式；群记忆与整理observe 模式没有任何执行副作用。群里学到的事实不进 Bot 的私有记忆。

10. 从第一天就守住的不变量

守住这八条，群聊就是往 MVP 上加东西，而不是推倒重来。

  1. 消息存作者，不存 user / assistant 角色。单聊就是两个成员的会话。
  2. 产品会话不等于模型会话。界面只读投影；Bot 的模型上下文可以重建、压缩、换模型。
  3. 每件事有且只有一个负责 Bot。执行者可以换，负责人不因改派而变。
  4. 所有干活路径走执行者端口。前台不长时间干活。
  5. 每个入站动作带幂等键（requestId、assignmentId、inputId）。先提交状态，再跑副作用。
  6. 看得到上下文不等于有权动手。权限按动作类别在代码闸上检查，和执行者是谁无关。
  7. 汇报是结构化的，不靠解析「看起来像做完了」的文字。
  8. 进度不等于消息。进度进卡片，消息只留给人需要看的四种情况。

11. 风险与待你拍板

待定 待定我的建议什么情况下改主意
「human agent」指什么两种都支持：Hermes Agent 走 ACP 适配器，真人走真人执行者如果是别的产品，告诉我名字，我去查它的接入面
