DSH Superagent：事件驱动的 IM 任务协作系统

解析 DeepSeek Harness 插件的路由、授权、执行、上下文流动与恢复机制，并给出适合 DeepBot 的整体架构。

调研日期：2026-11-09（America/Los_Angeles；抓取时 UTC 为 2026-11-10）
对象：deepseek-ai/dsh-superagent-prototype；package 版本 0.1.0
分析提交：8c32a9dc5d72c033816c6a8110b37f40cf94fba4

核心判断：这个插件的中心不是“一个 Bot 对应一条聊天”，而是“多个来源的事件，推动一个持续存在的协作体”。Router 判断新工作，Worker 承担任务，订阅把后续讨论直接送回任务；Policy 和 Mandate 决定能做什么，数据库和持久副作用队列保证工作能继续。

1. 设计思路：用户管理工作，系统管理执行会话

已实现公开原型面向一个 GitHub 仓库，监听 GitHub，并可选接入飞书。被允许的用户提出请求后，系统创建 Ticket，在独立 DSH Session 和目录中处理，结果送回原始讨论。产品原则是降低团队注意力成本：仅在有授权请求或明确规则时行动，仅在有结果、需要决定或确实无法继续时打扰人。[D1] [D2]

推断其核心抽象是“跨渠道持续推进的授权任务”。用户可以在飞书交代工作，在 GitHub 审阅，再回飞书追问；执行单元仍是同一个 Ticket，而不是三个互相不知道的聊天窗口。技术会话被放到后台，任务身份成为跨平台连续性的支点。

这与常见“Webhook → 一次 LLM 调用 → 回复”有本质结构差异：Ticket 可以等待、恢复、换 Assignment；Thread 可以关联多个任务；模型返回一句话并不自动意味着业务完成。

3. 核心领域对象：为什么要分这么细

对象职责与约束不应混同的概念
Source接收外界事件，持有读游标与自身 Bot 身份；过滤自己的消息，声明读和写能力。不是一个模型 Agent。
Trigger不可变输入事件，保留发送者、时间、所属 Thread；ID 用于去重。事件不一定是新任务。
Thread来源定义的时间有序讨论，保存订阅、待评估事件和 Decision 历史；每个 Thread 最多一个 Eval。不是模型 Session；一个 Thread 可有多个 Ticket。
Correlation同一 Trigger 所属多个 Thread 之间的关联，补充判断证据。关联不自动路由任务。
Policy / Eval版本化规则；确定性 Gate 与模型 Assessment 共同判断新工作。模型不能通过一句解释绕过硬检查。
Mandate记录授权强度、范围、来源身份、策略版本和匹配规则。后续消息不是自动扩权。
Ticket被授权的工作单位，拥有 Inputs、Channels、Assignments 与结束状态。不跟随模型 Session 的 busy / idle 简单变化。
Assignment / Executor一次派工绑定；Executor 是执行端口，具体实现是 DSH Session 和目录。重新派工可以保留原 Ticket、代码分支和 Session。
SubscriptionThread 到 Ticket 的多对多消息路由。读取上下文不代表发起新工作的权限。
Channel / Outbox回复地址与持久发送请求、回执。这里的 Channel 是输出端口，不等于 OpenBot 的内部协作群。

依据：[D6] [D5]。

4. IM 通信：新请求走路由，后续讨论走订阅

4.1 接入的真实实现

已实现飞书插件启动 lark-cli event consume im.message.receive_v1 --as bot 子进程，逐行解析事件；断开后退避重连。同时有聊天历史补读和订阅话题轮询。Trigger 保留 messageId、chatId、rootId、parentId、mention / direct 等来源信息，以稳定消息 ID 去重。首次建立历史读游标时从当前时间开始，不能理解为自动导入所有过往聊天。[D7] [D8]

GitHub 侧使用专用账号的 CLI 拉通知、Issue / PR / 评论与 CI 变化，按 Thread 保存读取状态。它不是要求每个 GitHub 事件都从 webhook 进入的实现。来源负责把 GitHub 和飞书各自的协议映射到统一 Trigger / Thread / Channel。[D9]

4.2 一条飞书请求如何走到交付

用户 @Bot：修复登录错误
  1. Feishu Source 记录 Trigger，标出 actor 与 replied-to 信息
  2. Engine 去重 → 保存 Thread 时间线
  3. 若没有已有 Ticket 承接 → Gate → Router 路由 / Assessment
  4. accept → Ticket + Mandate + 首次 Assignment + 订阅，事务提交
  5. Effects.launch → 准备目录 → worker-<ticket-id>
  6. Worker 在原消息下确认一次 → 执行 / 验证 / 创建 PR
  7. PR Thread 绑定 Ticket；Review / CI 作为 Input 到达 Worker
  8. Worker report：ready / blocked / failed / human_action 等
  9. Router 与领域回复规则 → Outbox → 原飞书话题
 10. 相关 PR 达到完成规则后，Ticket 结束并保留订阅

这是按实现重构的示例，不是本次真实运行记录。依据：[D6] [D10] [D11]。

4.3 用户边执行边补充，不必重新召唤主路由

已实现一个人的消息已通过订阅到达任务时，通常由 Worker 拥有并处理，不再重复做新任务 Eval。Worker 判断超范围或应由别的 Ticket 处理时，显式 handback；只有没有其他 Ticket 继续拥有该消息，才进入新的评估。主 Session 收到 follow-up notice，但不能趁 Worker 正处理时另开重复任务。[D12]

只为参考而 follow 的 Thread 属于 context-only：它能补充事实，但不获得该线程的人类 follow-up 所有权，也不能靠那里的消息恢复一个已结束任务。自动机器人与 CI 也不能像人的跟进一样任意恢复已结束 Ticket。被人明确停止的 Ticket 则不自动恢复。[D6] [D12]

4.4 通知设计：少而有用

协议区分 acknowledgement、answer、result、attention，普通进度主要留在 Ticket。需要人决定时，Worker 必须使用结构化 human_action，主 Session 将问题转回目标消息或最初会话。这样不会靠模型输出里有没有“请确认”来猜测任务是否受阻。[D13]

5. 授权与主动性：上下文可以广，授权必须窄

已实现Gate 先检查来源身份、allowed list、是否直接指向 Bot、来源 admission table 与 Bot 列表；模型再判断内容含义和规则匹配。明确请求与推断候选是两类强度。不能把“系统读到了消息”理解为“这人授权了所有可调用工具”。[D12]

模式推断型请求明确授权请求
off不进入推断候选处理。仍可正常处理。
observe（默认）评估并记录 would accept，实际不接单。仍可正常处理。
auto匹配至少一条启用规则后可接单。仍可正常处理。

Mandate 是不可变的授权依据。扩展范围原则上需要新 Ticket；Policy 变更使过时 Eval 重新排队，对相关运行任务投递变更通知，并不一律立即杀掉任务。已结束 Ticket 恢复前重新校验授权是否仍成立。不同 Source 的身份不做硬编码统一账号映射，团队可用 skills 说明人物关系，但这不会自动变成权限合并。[D12] [D13]

对 DeepBot 的建议：将 contextScope、actionScope、replyScope 分开存储和检查。群里有人贴出“忽略先前规则”的文本，可以作为资料进入上下文，但无权改变 actionScope。

6. 运行时：低延迟 Router 与有状态 Worker

6.1 Router 不做慢工作

已实现主 Session 负责接受、关联、拒绝、停止与协调，技术实现交给 Worker。Router shell / job 等待默认短返回，并对 sleep、过长 shell timeout 和 job wait 有额外限制；主 Session 应尽快结束空闲轮次，由候选、报告和结果消息再次唤醒。[D13] [D14]

推断这样控制的是调度层被长命令堵住的风险。它不意味着模型具有真正的并行认知；并发来自多个 Session 与可调度的 Inbox。

6.2 每个 Ticket 一份执行状态

Worker Session ID 由 Ticket 推导，工作目录默认在 <stateDir>/work 下。prepare command 通常创建 git worktree，首次目录缺失才运行，超时上限 10 分钟；没有配置 prepare 时就是空目录。Worker 使用专门 preset，普通长命令 5 秒后转后台以便下一个步骤接收补充消息。[D10] [D15]

并发额度覆盖启动准备、激活 turn 和后台任务，不只是模型 HTTP 请求数。普通并发之外还有一个供人的消息或状态请求使用的额外槽，且唤醒优先于新任务启动。轮次结束但后台 shell / subagent 仍忙时保持槽位；交给人 review、回答问题或报告阻塞时可释放槽。[D10] [D15]

6.3 两套状态不能混为一谈

状态层示例表达什么
Ticketopen / ended；可在授权有效时恢复。工作是否仍存在。
Assignmentpending → running → ended。这次执行绑定的寿命。
派生工作阶段working / queued、idle、person / answer、person / review、person / blocked、person / failed、person / delivery。此刻在等谁、为什么未推进。
报告progress、waiting、ready、blocked、failed、dropped。Worker 明确回报的工作事实。

没有 PR 的 ready 可完成 Ticket；有 PR 的 ready 进入等待 review，结束要看跟踪的 PR 关闭/合并规则及后续工作是否处理完。一次模型 turn 结束也可能只是等待下一条 Trigger。[D10]

6.4 真实的隔离边界

目录和 Session 分离减少上下文串扰与代码冲突，但两个 preset 都以当前 OS 用户的 danger-full-access 运行。账号 wrapper 和 blocked command 只是默认路由，绝对路径执行仍可能绕过，源码文档也明确不把它们当安全边界。专门 OS 用户、容器或隔离主机属于额外部署选择。[D16]

7. 上下文共享：结构化引用与定向投递

已实现共享的基础是持久对象之间的关系：Trigger 属于 Thread，Ticket 订阅 Thread，Assignment 属于 Ticket，Report 与 Input 指向具体工作。Router 读任务卡片即可知道全局概况；Worker 读自己的原始输入与任务资料完成工作，不必把所有 Worker 的完整上下文拼成一个超级 prompt。[D6] [D17]

7.1 小内容内联，大内容保留指针

cards.ts 生成受限卡片，包含 preview、完整字符数、对象 ID 与 read 路径；orchestrator_read 按 resource 与 offset 分页读取原文、报告、历史和源平台资料。默认文本页约 4,000 个 UTF-16 code units，列表默认 20 项、最大 50 项。引用关系是业务对象图，不是另建了一套向量数据库。[D17] [D18]

7.2 三条跨任务信息路径

  1. 订阅：Thread 新 Trigger 定向进入订阅 Ticket 的 Inputs，活跃任务可持续接收 review 与 CI。
  2. 显式关联：主 Session attach 需要消息明确指向某项工作，单纯主题相似不够，避免把整个群话题错误并入旧任务。
  3. 简短事实转交：主 Session 用 ticket note 给另一个任务事实，默认长度受限，且不授予权限。

应用工具对 Worker 的读取范围做检查：只能读取自己有权接触的 Trigger / Thread / Ticket 资源；共享 Thread 的读取不会连带开放其他 Ticket 的内部详情和 Decision。这个应用层边界仍不能替代前述 OS 隔离。[D17]

7.3 “送进 Inbox”还不等于模型已经读过

AgentDelivery 将稳定 request ID 转为稳定 MessageId，对 live events、持久历史、nextTurn 和 nextStep inbox 查重；确认前 flush session persistence。领域层另记录 input delivered、进入 session history、后续 report / turn end 等事实，区分“已排队但未读”和“已消费”。重试 Assignment 会重送未消费输入，并清理残留等待副本。[D19] [D10]

建议这是 DeepBot 最值得补上的协议细节：不能只用“写入 stdin 成功”作为 Agent 已处理消息的证据。

8. 记忆设计：有可恢复状态，但没有完整长期记忆子系统

层次本原型已经具备尚不能据此声称
任务事件记忆Trigger、Decision、Mandate、Inputs、Reports、Assignments 等持久台账。自动提炼跨项目通用经验。
工作会话记忆DSH Session 历史、可续用会话、按 Ticket 读取 transcript。插件实现了独立完整的压缩与向量召回系统。
团队知识版本化 prompts 与按需 skills，包含身份说明、流程和交付要求。每次任务后自动学习并合并知识。
按需回忆ID 引用、卡片、分页资源、源平台原文读取。全局语义检索、置信度管理和自动过期。
运行缓存有界 TextCache、部分标签与读分页缓存。持久记忆；重启会丢，分页可能要从 0 重新读。

已实现src/core/memory.ts 的 MemoryRepositories 是用于测试与临时 Engine 的内存 Map 仓储，支持 rollback；它不是 Agent 的长期记忆模块。公开原型的独立持久表与工具中，未发现 OpenBot 那种专门的 remember / forget / essential / searchable 事实记忆流程。[D20] [D21]

prompts 在每次模型请求重新组合，保存时用 base revision 防冲突，每次保存产生不可变版本。Policy 放在末尾，以免策略变更使前面稳定文本改变；Worker 还读 DSH coding prompt 与仓库 AGENTS.md。这些是配置与知识供应机制，不应与模型自主长期学习画等号。[D13]

推断其强项是“记住这项工作为什么开始、现在怎样、去哪里找证据”；弱项是“运行数月后提炼哪些稳定知识、忘掉什么、如何跨任务安全复用”。本次未找到独立语义 Watchdog、分布式迁移调度或全局向量记忆的实现，不能从设计文章标题推导这些能力已在该插件交付。

建议的互补关系：用 DSH 风格的任务台账负责可追溯与恢复，用 OpenBot 风格的事实记忆负责长期偏好和经验；所有摘要、记忆和检索结果都保留可回到原事件的证据引用。

9. 持久化与恢复：事务决定状态，副作用队列推进世界

9.1 核心存储

已实现Runtime 锁住 stateDir 后打开 orchestrator.sqlite，避免多个进程同时迁移和写入。主要表包括 trigger、disposition、trigger_thread、thread、ticket、decision、effect、outbox、kv；活动集合用生成列与索引读取。DSH Session 历史属于宿主持久化，并不全部塞进同一业务数据库。[D4] [D21]

Effect 类型作用恢复行为
assessment将候选送入主 Session。投递成功才开始 Eval 截止时间。
launch准备并启动 Assignment。无槽位则延后；瞬时失败有界重试，其他失败记录到 Ticket。
delivery向 Worker 投递 Inputs。退避重试，单独显示未送达问题。
relay / notice回传报告或不唤醒式通知。各自保序，失败阻挡后续同类消息。
reply向外部 Channel 发消息。Outbox receipt 与持久 effect 一起写入，再异步发送。

副作用键由 kind / key 唯一标识；当同一待执行键再次入队，会替换 payload 而保留排序。后续实现必须明确 key 是“一次命令的 ID”还是“可合并状态的 ID”，否则可能把真实的新变更误当重试。[D22]

9.2 外部消息去重落实到平台

飞书发送携带 --idempotency-key message.id；GitHub 评论嵌入稳定隐藏标记，重试前检索自己已发的评论。Outbox 保存 pending / sent / dropped 回执。相同 Ticket 同一会话的消息正常保序，但前一条连续失败达到阈值后不再无限阻塞后面消息，属于有例外的保序。[D11] [D23] [D24]

推断这是可靠重试＋幂等补偿；不能扩展宣称为所有工具、所有平台的分布式 exactly-once。尤其 GitHub 的“先查标记再发”依赖单实例调度与平台可见性，任意 shell 外部操作更需要恢复前检查真实状态。

9.3 重启、暂停、失败

  • 重启：忙碌 Assignment 结束并建立新 Assignment，保留 Ticket、目录、分支、Session 和待处理 Inputs，恢复提示要求先检查 Git、目录和 GitHub 再重复外部操作。
  • 已阻塞 / 失败：自动 CI 和 Bot 输入继续记录，但暂停自动唤醒；人的新消息或显式 retry 可解除。
  • 处理暂停：停止新评估、派工、输入投递与回复；Source 仍接收记录，运行中的 turn 不强制中断。
  • 输入与回复失败：分别可见，退避重试；永久不存在的目标记录为 dropped，不能伪装为 sent。
  • 积累数据：文档明确旧 Trigger、Decision、Ticket、回执、配置版本尚无清理，长期会增长；生产化需要 retention 与归档策略。

依据：[D10] [D21]。可靠性的边界是“状态可查、工作可恢复”，不是“重启完全没有行为差异”。

11. 面向 DeepBot 的整体架构设计

建议以下是组合设计，不是两个项目中任何一个的现成实现。目标是：一个 Bot 可以拥有多项进行中的工作，用户从桌面或 IM 都能自然继续，任务和记忆边界可解释，进程重启后能够查证并恢复。

11.1 与当前工程的接点

本地已核验当前 packages/agent/src/main.ts 打开 Pi Durable SQLite、创建一个 root、调用 resume，再向桌面推送 snapshot；stdin 协议只有 input 与 abort，requestId 可选，尚无 botId / threadId / taskId。桌面是 NSH / QuickJS，经 Rust 与 Node sidecar 用 JSON-lines 通信。因此可沿用这条边界，把业务控制面放在 Node 侧；不需要将 NSH 当成 React 浏览器，也不需要为调研改动 UI。[本地 main.ts] [本地 protocol.ts]

11.3 运行契约与 IM 协议

命令（建议）：
message.submit { requestId, botId, threadId, content, replyTo, attachments }
task.steer     { requestId, taskId, expectedRevision, content }
task.cancel    { requestId, taskId, expectedRevision, reason }
attention.reply{ requestId, attentionId, actorId, value }

事件（建议）：
message.accepted / task.queued / run.started / run.delta
tool.started / tool.finished / attention.required
run.finished / task.stateChanged / outbox.delivered / outbox.failed

公共字段：eventId、sequence、botId、threadId、taskId、runId、timestamp
恢复：snapshot + afterSequence 增量；consumer 可检测断点并补读

已有 requestId 可以升级为强制幂等键；abort 应升级为带 taskId / runId 的定向取消。不能让切换到另一 Bot 后的旧停止按钮误停新工作。外部 connector 只认业务 API，不直接操纵 Pi Durable 的某个 root。

11.4 上下文组装顺序

  1. 宿主硬规则与能力约束（代码执行，不能仅靠 prompt）。
  2. Bot 指令、任务 Mandate 和明确目标。
  3. 本任务已核验状态、未解决问题、最新用户补充。
  4. 允许范围内的 essential 记忆和选中的 skills。
  5. 相关历史摘要＋最新原文＋证据指针。
  6. 检索所得材料与工具结果，明确标注来源为数据。

Context Builder 先做 ACL 与 scope 过滤，再做相关性排序和预算裁剪。不要先全库向量检索再指望模型自觉不使用私人命中项；摘要必须保留原文 ID，用户纠正之后使旧摘要失效或重建。

11.5 记忆闭环

任务事件 / 用户明确纠正
  → 候选事实（附来源，不直接成为权威）
  → 去重、冲突检查、作用域与敏感字段检查
  → 成功提交 / 用户采纳
  → essential 或 searchable
  → 任务检索时过滤权限、时效、冲突版本
  → 使用后保留命中与证据记录
  → 用户纠正、过期、替代、删除及索引清理

首版可用 SQLite 文本检索，但必须用中文句子、别名、长短词做召回验证；是否加 embedding 应由真实命中率决定。摘要、对话历史、稳定偏好和任务结论分别管理。未验证的模型猜测不应自动晋升成 essential；跨 Bot 提升为 shared 记忆应有明确规则或人工确认。

11.6 持续在线与安全边界

当前侧车在 stdin 关闭时退出，生命周期跟随桌面宿主；这能支撑本机桌面使用，但关闭桌面或机器休眠后不能继续收 IM。若目标是常在线 Bot，应让一个独立本地 daemon / 服务成为唯一执行宿主，桌面通过受鉴权 IPC 连接；再考虑远程部署。进程 supervisor 负责进程存活，Task Engine 负责恢复，业务进度检测负责“活着但没推进”，三者分工。

多租户或接入不可信群聊前，需要独立执行账号/容器、文件根目录与工具 capability 白名单、出站目标限制。个人可信 MVP 可先保留单用户主机结构，但仍要区分“能读哪些上下文”和“能执行哪些动作”。

12. 实施顺序与可核验的验收标准

阶段建设内容验收门槛
P0：单 Bot 持久闭环必填 requestId，Inbox / Outbox，task / run IDs，状态事件与重启恢复。同一消息重试只开一项任务；在入队、执行、结果回送三处崩溃不丢任务归属；未知外部结果能核查。
P1：多 Bot 与独立任务BotProfile、RuntimeAdapter、任务队列、并发槽、定向 steer / cancel。两项任务并行时不串消息；停止 A 不影响 B；人的补充不会永远排在新任务之后。
P2：首个 IM 来源飞书 Source、actor Gate、Thread 关联、订阅、人工问题与原路回送。群聊 @、私聊、回复链、Bot 自身消息、离线重连和撤回原消息均有可解释结果。
P3：记忆与上下文记忆作用域、essential / searchable、摘要指针、历史回读、纠正与删除。跨用户私有记忆不可读；失败任务不写成功结论；清空后在途写入不复活；中文召回达到预先定义的目标。
P4：主动事件与常在线observe / auto 策略、定时来源、后台服务、健康与业务进度检查。observe 零执行副作用；auto 必须命中规则；源故障可见；关闭桌面后服务持续并正确回送。

必须纳入测试的故障矩阵

  • 重复 / 乱序 / 编辑消息；同一外部 ID 在不同账号下不误碰撞。
  • 用户在旧 Thread 开新工作、显式引用旧任务、仅语义相似但实际无关，三者正确区分。
  • Router 忙、Worker 忙、后台工具忙、等待人工，均允许精确停止和保留补充消息。
  • Policy 在 Eval 期间变化；已结束任务恢复时授权已撤销。
  • 模型超时、429、工具成功但响应丢失、外部已发消息但本地未记 receipt。
  • 摘要遗漏条件、长期记忆冲突、中文检索漏召回、手动清空与后台 review 同时发生。
  • 会话恢复成功但业务尚未完成；PR 已创建但未审查；结果已生成但 IM 回送失败。

建议持续观察接收至落库延迟、排队时长、任务完成率、重复外部动作数、回送失败率、待人工时长、每任务模型成本、记忆纠正率与检索命中率。这里没有编造实测数据或预设两个项目的性能高低。
