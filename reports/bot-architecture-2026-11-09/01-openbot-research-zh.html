核心判断：OpenBot 将 Bot 建模为一个长期存在的“工作成员”：身份、职责、工作目录、技能和记忆持续存在；聊天、群聊任务、定时任务只是它的不同工作入口。IM 风格的消息界面背后，是持久邮箱、线程调度器、Provider 适配器和分层上下文系统。

1. 产品与领域模型

已实现官网将它定位为可运行在个人电脑或服务器上的 AI 团队工作区。桌面端使用 Electron 与 SolidJS，业务运行时主要位于 TypeScript 后端；云端账号、连接协调与本地执行分开。这里的 OpenBot 不是同名机器人硬件项目，也不是 OpenClaw。[官网] [O1]

对象作用设计价值
Agent / Bot名称、职责、Provider、模型、工作目录、指令、技能、记忆与权限。更换模型或新建会话不等于换了一个成员。
主聊天与 side thread同一 Bot 的多条对话；各有队列、会话与执行结果。身份复用，临时任务上下文分开。
Channel内部共享群聊：目的、成员、负责人、公共消息、任务与派工。让人看到协作，并让调度器拥有明确的责任人。
Task / Assignment / Turn群聊任务描述工作，派工绑定执行者，Turn 是一次模型执行。side thread 在兼容接口中也仍称 task。必须识别同名概念的上下文，不能把每次聊天回复都当独立任务。
Mailbox delivery一次可跟踪、可去重、有状态的投递。消息先成为持久工作，再由运行时处理。
Provider sessionCodex、Claude、ACP、Pi 等原生执行会话的绑定。产品会话与模型厂商会话解耦。
Messaging connection / link外部平台连接，以及外部对话到 Bot 执行线程的映射。外部群聊不混入个人主聊天。

依据：[O1] [O2] [O3]。

推断这是“本地主机为执行权威、客户端为投影”的结构。UI 不直接修改 Provider 状态，Provider 事件先进入业务服务与 SQLite 投影，再推送给客户端。因此多端界面和模型执行并非同一个生命周期。[O1]

3. 一个 Bot 从创建到完成工作的完整链路

  1. 配置身份：建立 Bot 记录与工作目录，选 Provider、模型、权限、技能；长期行为放在工作区 AGENTS.md，只有 CLAUDE.md 时使用后者。简介用于给其他成员理解职责。[O3]
  2. 接入消息：入口识别用户、平台、外部会话、附件和消息 ID；外部输入转换为内部统一消息，保留来源，不直接伪装成宿主指令。[O2]
  3. 确定归属：直聊指向 Bot；内部群聊确定任务 owner；外部线程优先使用既有 link，首次对话交给平台协调 Bot。[O2]
  4. 持久入队：Mailbox 保存消息、投递与附件引用，幂等键返回原 receipt；业务接受与模型开始不是同一个事件。[O4]
  5. 竞争执行槽：DrainScheduler 检查当前 lane、任务并发、Provider 能力、用量与主机资源；不具备条件的消息保持等待并附原因。[O5]
  6. 构建上下文：按工作类型选择真实执行线程，拼装角色规则、记忆、历史和当前任务；按需恢复或替换 Provider session。[O6] [O7]
  7. 执行与交互：接收模型文本和工具事件；处理人工审批、补充问题、停止、工具调用、同伴委派及附件产出。[O1] [O3]
  8. 提交结果：对话与 mailbox 状态落库；完成轮次才提交暂存的 Bot 记忆；消息与附件投影发送给对应界面或外部平台。[O8]
  9. 后处理：触发群聊摘要、符合条件的后台记忆整理、定时任务后续流程；闲置原生会话释放进程，但保留恢复身份。[O6]

建议对外状态至少区分“已接收、排队中、执行中、待人工、已产出、回送失败”，不要用一个 busy 布尔值承担全部业务含义。

4. 三种 IM 通信，三种不同语义

4.1 内部群聊：共享消息，不广播唤醒所有 Bot

已实现Channel 保存公共 transcript；每个 channel × agent 组合有独立执行线程。明确接收者、回复归属等情况直接路由；需要判断时，使用 lead 的模型开一个没有工作工具的路由会话。任务可以派给一个或多个成员，但只有任务派发和等待中的结果等事件启动执行，聊天可见不意味着所有成员都要发言。[O2]

群聊有子任务派发和所有权移交两种操作。前者保留父任务负责人，后者改变负责人；根请求自动派工有数量上限，固定快照中每个 Channel 同时活跃派工上限为 2，根请求自动派工上限为 8。旧派工不能凭过期 revision 完成被用户纠正的新任务。[O2]

4.2 Bot 私信协作：请求、结果与唤醒组成闭环

已实现同伴通过 send_message 等工具交接工作；请求包含完整 brief，结果必须显式回给请求者。同一请求交给多个同伴时，已返回结果可等待其余副本结束后合并唤醒请求者；人的新消息可打破这种等待。中断工具限制调用者只能停掉由自己请求启动的工作。[O3]

推断这接近“持久信箱＋任务关联”的 actor 风格，而不是简单 HTTP 同步调用。长期 Bot 是收件人，运行中的模型会话只是当前处理者。

4.3 外部 IM：平台适配、对话关联、结果回到原处

外部 mention / 私信
  → 平台适配器 / Signal relay
  → MessagingService 解析与去重
  → connection + conversation link
  → MessagingThreads → mailbox → 独立执行线程
  → 本 Bot 执行，或 send_message 委派同伴
  → messagingReturn 携带原对话归属
  → 串行发送状态、答案、文件到原平台

已实现MessagingDriver 负责平台 API 与传输，MessagingThreads 不读取平台原始载荷。Slack 通过事件回调和 Signal socket 转发；Discord 由 Signal 持有 Gateway；Telegram 使用共享 Bot 与 chat 路由，主机通过受限远程调用发消息；WhatsApp 则有独立的客户端连接实现，不能把所有平台都概括为同一种 webhook。[O2] [O13]

需要保留两个限制：Slack 离线超出平台重试窗口会丢消息；Telegram 接入总是向平台返回 200，历史缓存与部分回复映射在内存中，不能推导出无限离线补偿。当前 mailbox 去重解决的是“重复处理”，不是“消息从未到达”。外部消息也不能默认具有个人会话的历史读取权限。[O2]

5. 运行时：Bot 持久，进程可释放

层次生命周期职责
Bot长期身份、目录、权限、技能、记忆。
逻辑线程长期或任务期消息顺序、会话隔离、业务归属。
Mailbox lane有工作时调度同一 lane 一次一个 turn；不同 lane 的并发受能力和限额限制。
Provider session可恢复、可替换厂商原生上下文、工具与恢复状态。
CLI / 工具子进程可释放计算与工具执行；不能充当唯一业务状态。

已实现同一 Bot 的 side threads 默认任务并发上限为 4；主聊天不计入 side-thread taskLimit。声明不能并发的自定义 ACP Provider 会限制整个 Bot 一次一个 turn。外部 messaging work 仍归于主聊天 lane 的调度，不应承诺每个外部线程都能自由并行。[O3] [O5]

定时 routine 使用临时 Provider 会话，不复用普通原生 session；可以显示在主聊天或专属 side thread，向后续会话提供 bounded handoff / digest。重启中断的临时 routine 会被标记 interrupted，不能称为所有任务均无缝续跑。闲置普通会话则可卸载进程并在下一轮恢复。[O3] [O6]

6. 上下文共享：按作用域构建，不复制整段全局历史

上下文共享方式隔离边界
Bot 指令与 essential 记忆在所属 Bot 的执行中供上下文组装使用。不是所有 Bot 自动共用一份人格和记忆。
个人主聊与 side threads历史工具可显式读取同一 Bot 的其他对话。从当前 reset 之后读；外部 messaging 不获得跨个人对话权限。
群聊公共 transcript、摘要、频道记忆、任务关联与上下文增量。执行线程独立；成员不依赖共享一条原生模型 session。
外部 IM当前 link 的历史＋connection 级事实，每轮重建。connection 级不是每个话题级；不等于私人记忆。
共同工作成果Shared 文件目录和共享 agent-data SQLite 表。共享文件是协作机制，不能视作强沙箱。

已实现群聊 context packet 上限为 120,000 字符，其中最近 transcript 预算为四分之一；超量旧消息形成摘要，原始请求仍放在 referenced messages，摘要只作参考。新一轮主要递送增量，避免再次注入本成员自己已经看到的输出。历史工具分页返回截断内容的下一段。字符预算不是 token 数，不能用来证明特定中文模型一定不会溢出。[O7]

更换 Provider session 时，handoff 最多 32,000 字符，包含近期消息、较早片段和部分工作步骤；历史工具按需补读。Provider 私有推理和完整内部状态不在跨 Provider 交接中。压缩则遵守各 Provider 能力：Claude 原生处理、部分 Provider 显式 compact、部分 ACP 无此操作。[O6]

对 DeepBot 的直接价值：把“共享”定义为有来源、有范围、可增量拉取的数据协议。共享任务结果和可核验资料，保留每个执行者的独立工作上下文。

7. 记忆设计：长期事实与聊天历史分工

7.1 已实现的数据结构

MemoryStore 抽取公共 CRUD，按 owner 分成 AgentMemoryStore、ChannelMemoryStore、MessagingMemoryStore。记录包含 ID、文本、manual / automatic 来源、sourceTurnId、创建与更新时间。Agent 记忆另有 inclusion、userControlled、revision。[O9] [O10]

层级注入 / 查询用途
Essential序列化后 8,192 字节的预算；包含 JSON 包装开销。稳定、高频、必须知道的事实。
SearchableSQLite FTS5 unicode61＋BM25；默认 5 条，最多 10 条；结果也受字节预算限制。低频但可检索的长期事实。
Historyhistory_search / history_read，分页与访问校验。发生过什么、做过什么、原始证据。
Channel / connection 记忆注入对应工作上下文，并提供相关工具。群聊或连接范围内的共同事实。

已实现这是一套文本与词法检索机制，不是已部署的向量知识库。中文分词、同义词召回和语义相似检索不能凭 FTS5 的存在就认定有效，需要单独评估。[O10] [O11] [O14]

7.2 写入不是工具一调用就永久生效

Agent 的 remember / forget 先暂存到当前 turn，成功完成才提交。失败或用户中断不留下这批改动；手工清空通过 epoch 防止在途 turn 把旧记忆写回来；更新时间与 selection revision 用于并发冲突检测。后台 review 避免覆盖用户编写、用户明确选择或读取后已被修改的记忆。[O8]

7.3 后台整理与遗忘

默认每段对话累计 20 个完成 turn 后整理；达到至少 3 个新 turn 且闲置 15 分钟、清理聊天、关闭有新内容的 side thread 也可触发。Channel、messaging 和 routine 不计入这套自动 review。它使用独立、无工具的模型调用产出 add / update / forget JSON，然后走相同预算与冲突校验。可关闭，也可选择 10 / 20 / 40 turn 阈值。[O6]

review 游标与计数主要在内存中，重启后从最近消息重新读取；这不同于一个严格持久、精确一次消费的记忆提取流水线。删除记忆时还处理相关旧事件/receipt，避免仅从 UI 隐藏、底层仍能恢复原文。[O6] [O9]

7.4 群聊隔离是有方向的

开启 isolated Channel 后，群聊中的通用 remember 被改写为 channel memory，且不能按 memoryId 修改 Bot 私有记忆；但 Bot 自己的记忆仍可进入 Channel。它阻止“群聊学到的事实自动外溢”，并不是双向严格信息隔离，也不是文件和 MCP 权限沙箱。[O2] [O7]

8. 持久化、恢复与交付语义

已实现openbot.db 保存 Bot、对话、投递、附件与 Provider session 绑定。群聊命令有事件日志和 command receipt；Mailbox 的幂等键用于跨重试识别原消息。ConversationRuntime 只是活跃状态和有限缓存，完整历史从数据库读取。附件提交与文件删除 outbox 分工，避免数据库成功、文件副作用失败造成失联。[O1] [O4]

Provider 自己的登录和 session 数据由 Provider 持有，因此备份 openbot.db 不等于备份所有原生运行状态。不能恢复原生 session 时，产品会话可通过受限 handoff 重建；这是业务连续性，不是模型内部状态的精确重放。[O6]

推断应分别衡量三类成功：消息已持久接收、模型工作已完成、外部平台已确认结果。网络未知结果、工具对第三方的副作用以及平台重试都需要独立核查，不能把本地幂等 receipt 宣称成跨系统 exactly-once。

9. 权限、扩展与部署边界

  • 主进程校验不可信 IPC，renderer 只使用受限接口；远程端通过协议能力协商演进。[O1]
  • 工作区权限、Ask first、Full access 与人机审批属于运行主机；不同 Provider 的沙箱支持有差异。[O1]
  • MCP 在主机层共享；专家 Bot 的差异往往在职责、技能和记忆，而不是独立连接一套应用账号。[O3]
  • Channel 成员列表选择可接任务的 Bot，不限制已认证服务器成员的人工读权限。若未来要多租户，需额外设计 ACL。[O2]
  • 公开仓库元数据标注 PolyForm Noncommercial 1.0.0；架构调研与直接复制实现是不同决策，引用代码前需核对适用许可。[O12]

10. 对 DeepBot 的启示与取舍

建议优先借鉴“持久 Bot＋多条任务线程＋持久消息投递＋分层记忆”。初期无需复制 OpenBot 的完整桌面、云账号、市场与多 Provider 体系。

应吸收解决的问题DeepBot 的最小实现
Bot 与 session 分离新聊天不丢人格、目录和经验。BotProfile 持久记录，Run 单独绑定底层会话。
Mailbox + lane忙时消息不丢，顺序可解释。SQLite inbox、幂等键、每任务串行、全局并发限额。
Context packet群聊与个人上下文相互污染。task / thread / bot 作用域过滤后组装，不全局拼历史。
Essential + recall无限记忆挤满上下文。少量常驻事实，更多事实按需检索；中文专门测召回。
暂存记忆与版本保护失败过程被记成成功、并发覆盖用户修改。成功 turn 提交候选记忆，带 evidence 与 revision。
原始记录与摘要并存摘要失真后无法还原依据。摘要引用 message IDs；允许回读原文。

OpenBot 最值得复制的是状态边界；不应机械复制其并发数、字符预算或所有平台接入方式。与 DSH 结合的整体设计见第二份报告第 11 节。

11. Bot 必要运行环节的验收清单

建议以下是 DeepBot 后续实现的验收目标，不是本次已运行的测试。

环节必须验证的场景
创建与配置Bot 重启后身份、目录、权限和模型绑定不变。
接入与归属相同外部消息重复投递只产生一次逻辑工作；私聊与群聊线程不串。
调度与补充长任务期间可排队、停止和收到补充；补充只进入目标任务。
协作同伴失败不会无限互相转发；结果回到真正请求者。
工具与人工环节待授权状态可恢复；未经授权的入口不能替用户确认审批。
上下文与记忆越权 recall 被拒绝；失败 turn 不沉淀成功事实；删除后在途写入不复活。
外部交付模型完成但消息发送失败可见、可重试；附件归属不变。
异常与长期运行在入队后、工具后、模型结束前和回送后分别崩溃，验证重复副作用边界。
可观测性message → delivery → task → run → tool → outbox 可追踪；记录排队时长、成本、失败原因。
