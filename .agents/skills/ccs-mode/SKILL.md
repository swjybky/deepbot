# ccs-mode

1. 默认直接执行。用户明确要求先复述时，用大白话说明目标、影响范围和验收标准。用户要求先确认时，得到同意后再执行。
2. 从[功能地图](../../../references/features/README.md)找受影响的功能，读对应页的入口、协议、可用场景和注意事项。涉及界面时，改动前按 [DESIGN.md](../../../DESIGN.md) 的「按需加载约束」读相关主题。
3. 按主要目标选一种任务类型，只读取对应剧本。任务中遇到其它类型的问题时，复用对应剧本的步骤。下面标出的路径都以 DeepBot 仓库根目录为起点。

| 用户主要想做什么 | 读取 |
| --- | --- |
| 修复已经发生的问题 | [.agents/skills/playbooks/fix-bug.md](../playbooks/fix-bug.md) |
| 新增功能或改变现有行为 | [.agents/skills/playbooks/feature.md](../playbooks/feature.md) |
| 查原因、梳理现状或判断优先查什么 | [.agents/skills/playbooks/investigate.md](../playbooks/investigate.md) |
| 对比几种界面或交互做法 | [.agents/skills/playbooks/prototype.md](../playbooks/prototype.md) |
| 用户明确说用指挥模式或领导模式：本对话领导，Codex 执行 | [.agents/skills/playbooks/command.md](../playbooks/command.md) |

4. 按[验证技能](../../../skills/verify/SKILL.md)验收，命令用法以 `pnpm --silent verify --help` 为准。一次做一件事，改动保持小而独立。验证行为时要用 verify CLI 在隔离实例里实际跑起来并观察结果，测试结果之外还要提供实际运行证据。界面改动按验证技能实际操作、截图，并对照设计条目看图核对。
5. **任何改动完成前，必须在最后一次修改后运行 `pnpm --silent verify check`，并全部通过。** 最后给出检查结果和相关证据链接，例如截图、接口 JSON、日志或场景报告。证据缺失时说明缺哪一项和原因。

## 改进剧本

用 ccs-mode 完成真实任务后，剧本有说不清、走不通、遗漏的地方，或者被用户纠正过，就回顾这次实际过程，修改对应剧本。每个剧本控制在一页以内，每步只写动作和可观察的完成标准。尽量指明实际用过的 verify CLI 子命令和功能地图条目，把用户纠正过的地方写进步骤，最后一步给出证据。判断问题出在哪一层、按层修复和定期体检，用 [ccs-retro](../ccs-retro/SKILL.md)。合作顺利、想把用户纠正或被验证的做法沉淀下来，用 [ccs-distill](../ccs-distill/SKILL.md)。

修改时，下列步骤必须保留。

| 剧本 | 须保留的步骤 |
| --- | --- |
| 修 bug | 用 verify CLI 复现并留下失败证据。查功能地图和代码，说明根因。修复后重跑同一场景证明已修好，再跑 `verify check`。按下文「错误变规则」防复发。 |
| 做功能 | 用户要求时复述需求。查功能地图确定影响范围，涉及界面时读 DESIGN.md 相关主题。实现后用 verify CLI 实际操作并截图，回归受影响功能，更新功能地图，再跑 `verify check`。 |
| 调查 | 先查证再给出建议。记录已知事实和实际查过的数据，例如日志、接口、数据库或 Git 历史。列出几个假设及各自依据，指出优先验证哪一个。 |
| 原型 | 读 DESIGN.md 相关主题。在同一轮准备两三个方案，用 verify CLI 分别操作、截图和测量。对比优缺点，交用户选择。选定后清理本轮未选中的方案。 |
| 指挥 | 仅在用户明确点名时使用。领导先查功能地图和设计主题再写任务书。界面任务先给用户看设计稿。任务书写明验收命令和证据格式。领导亲自看截图验收。最后 `verify check` 通过。 |

## 检验剧本

每次写完或大改一个剧本，提醒用户在全新对话里用一个真实小任务试跑。根据反馈修改剧本。

> 请只根据 ccs-mode 技能和相关剧本，完成这个任务：<真实小任务>。过程中如发现剧本说不清、走不通或遗漏的地方，任务完成后列出来。

## 错误变规则

这是全仓库唯一的防复发顺序，其它文档只链接到这里。代码出现缺陷、agent 漏做剧本步骤，或照做仍然出错时，从上往下选第一个能用的手段。

1. 改接口设计或类型，让错误写不出来。
2. 能自动判定的错误，先修存量，再加 lint 或检查。把规则来历登记到 [rules/README.md](../../../rules/README.md)。
3. 能自动复现的行为缺陷，补回归测试。
4. 能交给工具代办的操作，提议加进 verify CLI，写清做了什么、现有命令为什么做不到、建议的形式。用户同意后再改 `tools/control/`，并在 `tools/control/cli.test.mjs` 补回归。
5. 需要人判断的事，才补写对应剧本步骤或设计文档。工具或规则接手后，删去剧本里已被覆盖的说明。
